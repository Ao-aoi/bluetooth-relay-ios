# 解析部(Analysis/)の読み方

対象: `docs/Swift教材.md` の「0. 最低限の文法」と「7. Packet.swift」を読んだ人。
この文書は、その続きとして `Analysis/Sources/EcgCore/` の残りのファイルを扱う。Swift教材に書いた文法(`let`/`var`、`?`、`guard` など)はここでは説明しない。

解析部は、Python版(`kokolog_test` の `realtime/pipeline.py` と `20261110_viewer_realtime.py`)を書き写したもの。
どのファイルも「Python版のどの関数に当たるか」を先に書いておくので、Python版を横に開いて見比べながら読むとよい。

## 1. 全体の流れ

心電計から届いた1パケット(0.2秒ぶん、50点)が、どの順に処理されるか。

```
EcgPacket(105バイトを読む)                        Packet.swift
  ↓
EcgSession.onPacket  欠落を見つける                RealtimeECG.swift
  ↓
RealtimeECG.push     移動平均 → 帯域通過フィルタ    RealtimeECG.swift / SignalTools.swift
  ↓
RealtimeECG.detect   R波の候補を探す(findPeaks)   RealtimeECG.swift / SignalTools.swift
  ↓                  ① 張り付き区間の近くを除く     BeatCleaning.swift
RealtimeECG.afterNewPeak
  ↓                  ② 短すぎる間隔の偽ピークを除く BeatCleaning.swift
  ↓                  ③ 異常なRRIを補間する          BeatCleaning.swift
RealtimeRiR.beat     RiR・ΣRiR・La を計算する       RiRFilters.swift(基準プログラムのまま)
  ↓
BeatResult(1拍ぶんの結果)→ RealtimeECG.beats に追加
```

動きのパケットは `EcgSession.onGyro` → `ActivityEstimator`(Activity.swift)へ流れ、安静 / 軽い動き / 運動 を決める。
`Recording.swift` は、届いたパケットをファイルに書き、あとで同じ順に流し直すためのもの。

## 4. ファイルごとの読み方

### 4-1. Complex.swift(複素数)

Swiftには複素数の型が無いので、実部 `re` と虚部 `im` を持つ `struct` を作り、`+ - * /` と `exp` を定義している。

```swift
public static func * (a: Complex, b: Complex) -> Complex {
    Complex(a.re * b.re - a.im * b.im, a.re * b.im + a.im * b.re)
}
```

(a + bi)(c + di) = (ac − bd) + (ad + bc)i を、そのまま書いただけ。
`static func *` と書くと、`x * y` と書いたときにこの関数が呼ばれる。Pythonの `__mul__` と同じ仕組み。

`exp` は、オイラーの公式 e^(x+iy) = e^x (cos y + i sin y) をそのまま書いている。UnevenFilter が `exp(p[k] * T)` で使う。

### 4-2. SignalTools.swift(中央値・フィルタ・ピーク検出)

**median**
並べ替えて真ん中を取る。偶数個なら真ん中2つの平均。`numpy.median` と同じ値になる。

**BandPass(5〜25Hzの帯域通過フィルタ)**

- `sos` の3行は、Pythonで `scipy.signal.butter(3, [5/125, 25/125], btype="band", output="sos")` を実行して出た数をそのまま貼ったもの。Swiftでフィルタを設計し直すと、小数の最後の桁がずれる恐れがあるので、数を写した。
- `zi` も同じく `scipy.signal.sosfilt_zi(sos)` の値。フィルタを掛け始めたときに、波形が急に立ち上がったように見えないための初期値。
- `sosfilt` は、2次のフィルタを3段つないだもの。1段ぶんの計算は次の3行で、Pythonの scipy の中身と同じ式。

```swift
let y = c[0] * cur + z[s][0]
z[s][0] = c[1] * cur - c[3] * y + z[s][1]
z[s][1] = c[2] * cur - c[4] * y
```

- `filtfilt` は、前から1回、後ろから1回フィルタを掛けて、波形の時間のずれを無くす。その前に、両端を21点ずつ点対称に延ばしている(`2 * x[0] - x[i]` の部分)。端でフィルタが乱れるのを防ぐためで、scipy の `sosfiltfilt` が内部でやっていることと同じ。

**findPeaks(ピーク検出)**

scipy の `find_peaks(x, distance=, prominence=)` と同じ結果を返すように、3段で書いてある。

1. 両隣より高い点を全部拾う。頂上が平らなら、その真ん中を取る。
2. `distance`(65点 = 0.26秒)より近いピークは、高い方だけ残す。高い順に見て、近くの低いピークに `keep[k] = false` を付ける。
3. 周りからの突き出し(prominence)が足りないものを除く。左右それぞれ、自分より高い点に当たるまで進み、その間の最小値を求める。2つの最小値の高い方からの高さが、突き出しの大きさ。

### 4-3. BeatCleaning.swift(①②③)

R波検出の後始末。どれも「未来のデータを見ない」(causal)版。

**① clipDropoutMask**
記録値が 0〜1 か 16382〜16383(14bitの上下限)に張り付いた点と、その後 `margin` 点(0.15秒 = 38点)に `true` を付ける。
`lastRail` に「最後に張り付いた位置」を覚えておき、そこから何点離れたかで判定している。過去だけを見るので、Python版の `rolling(...).max()` と同じ結果になる。

**② sanitizeCausal**
新しいピークが来るたびに、直前に残したピークとの間隔 `rrNew` を見る。

- 短すぎる条件: `rrNew < max(0.26秒, 0.55 × これまでの間隔の平均)`
- 平均は指数移動平均(`ema`)。新しい間隔を 15%、これまでの平均を 85% の重みで混ぜる。
- 短すぎたら、振幅の小さい方を捨てる。前のピークの方が小さければ前を捨てて、もう一度比べ直す(`continue`)。今のピークの方が小さければ今を捨てる(`p = nil`)。
- 捨てる数には上限(`maxRemoved`、全体の12%)がある。これを超えて捨て続けないための歯止め。

`var p: Int? = p0` で「今のピーク、ただし捨てたら nil」を表し、最後に `if let q = p` で残すかどうかを分けている。

**③ repairCausal と fillLinear**
各拍について、自分と過去10拍の中央値 `med` を求め、次のどちらかなら異常とする。

- (a) 比: `rri < 0.6 × med` または `rri > 1.5 × med`
- (b) 差: `|rri − med|` が、周りのばらつきの6倍を超える。ばらつきは MAD × 1.4826(正規分布の標準偏差に合わせるための係数)で、8ms より小さくはしない。

異常な拍が連続している区間ごとに、`fillLinear` が前後の正常な拍のRRIを直線で結んで埋める。横軸は拍の番号ではなく時刻(サンプル番号)。後ろにまだ正常な拍が来ていない区間は `nan` にしておき、次の正常な拍が来たときに埋める。

### 4-4. RiRFilters.swift(RiRの計算。式を変えない部分)

基準プログラム Uef190901 の式を、そのまま書き写した部分。CLAUDE.md の約束どおり、**式は変えない**。読むときは「Python版と同じ式か」だけを確かめればよい。

**RiRConst**
フィルタの極(`poles`)と利得(`gains`)。LF / HF / VF の3つの帯域それぞれに4つずつ。Python版の定数をそのまま写してある。

**UnevenFilter(不等間隔の帯域フィルタ)**
RRIは拍ごとに間隔が違う(不等間隔)ので、通常のフィルタは掛けられない。このフィルタは、前の拍からの経過時間 `T` を使って状態 `x` を更新する。

- `if (T - (u / 1000.0)) > ngSpan` の分岐: 前の拍から0.8秒以上空いた(拍が抜けた)とき。状態を作り直し、出力を `-1`(無効)にする。
- それ以外: 3つの項 `term1 + term2 + term3` で状態を進め、4つの状態の和の実部の2乗を出力 `y` にする。

`term1` などを別の変数に分けているのは、複素数の長い式を1行で書くと、Swift のコンパイラが型を決めるのに時間がかかりやすいため。計算は1行で書いたときと同じ。

**MovAveFilter(帯域パワーの移動平均)**
直近180秒(`intSpan`)の `y × RRI` の合計を、RRIの合計で割る。

- `buf` は輪のように使う配列(リングバッファ)。`idx` が書き込み位置、`kmin` が180秒の窓の先頭。`% buflen` で末尾まで来たら0に戻る。
- 窓から外れた古い拍は、`while span > intSpan` で合計から引いていく。
- 有効な拍が `validSpan`(120秒)ぶん溜まるまでは `power = -1`(まだ出せない)。画面の「準備中(○ / 120 秒)」はこの `sumt` を表示している。

**FatigueEstimator(ΣRiR と La)**
直近120秒の RiR を台形の面積で積分して ΣRiR にする。窓の端からはみ出した部分は、直線で按分して引く(`newy` の計算)。
`seeded` は、最初の1拍で幻の0の点と積分してしまう基準プログラムのバグを避けるための印(CLAUDE.md の変更履歴にある修正)。
`La` は、RiR が 0.3 以上の拍について `ΔHR × RiR` を積分し、`18 − 14 × exp(−積分 / 50000)` で求める。

**RealtimeRiR(1拍ずつ与える入口)**
状態を4段階で持ち、拍が来るたびに1段ずつ進む。

| 状態 | 何を待っているか | その拍でやること |
|---|---|---|
| `waitForFirstR` | 最初の拍 | 3つの UnevenFilter を作る |
| `waitForFilterOutput` | フィルタの最初の出力 | 3つの MovAveFilter を作る |
| `waitForFirstRir` | パワーが有効になる | FatigueEstimator を作り、`ok` へ |
| `ok` | なし | 毎拍 RiR・ΣRiR・La を出す |

`var ll: UnevenFilter!` の `!` は、「作る前は空だが、使う時には必ず作ってある」という意味。この状態の順番があるので、空のまま使われることはない。
`ll.y < 0`(拍が抜けた)ときは、何も出さずに `nil` を返し、`reseeds` を数える。

`RiR = VF / (LF + HF + VF)`。分母が0のときは0にしている(Python版と同じガード)。

### 4-5. RealtimeECG.swift(全体をつなぐ所)

**push(サンプルを受け取る)**

1. 記録値の下位14bit を取り出し、中心の 8192 を引く。
2. 5点の移動平均。250Hzでは5点がちょうど50Hzの1周期なので、電源の雑音が消える。前のパケットの最後の4点 `maHist` を覚えておき、パケットの境目でも途切れないようにしている。
3. 直近10秒(2500点)だけを残し、毎回 `filtfilt` を掛け直す。
4. `detect()` を呼ぶ。

毎回10秒ぶんを掛け直すのは、`filtfilt` が後ろからも掛けるフィルタで、新しい点が来ると直前の点の値も変わるため。

**detect(R波の確定)**

- 10秒の中で `findPeaks` を掛け、見つかった位置に `fOff`(窓の先頭の通し番号)を足して、測定開始からの通し番号 `g` にする。
- 末尾0.6秒(`lookahead`)より新しいピークは、まだ確定しない。後ろの波形が来ると位置や有無が変わることがあるため。アプリでR波が約0.6秒遅れて出るのはこのため。
- 同じピークを2回数えないよう、`lastConf` より後のものだけを取る。
- ①のマスクに当たったピークは捨てる(`droppedClip` を数える)。

**afterNewPeak(②③ → RiR)**

1. ②で残すピーク `kept` を決める。
2. 直近300拍(`tailBeats`)について、ピーク間の間隔から RRI[ms] を作る。
3. ③で補正する。
4. まだ RiR に渡していない拍(`committedSample` より後)を、`rir.beat` に1拍ずつ渡す。

最後の1拍は渡さずに保留する(`limit = cnt - 1`)。次のピークが来たとき、②でその拍が取り消されることがあるため。③で `nan` のまま(後ろの正常拍待ち)の拍も保留する。

**gap(受信の欠落)**
0.5秒以内の欠落は、直前の値で埋めてつなぐ。それより長ければ、波形とピークを全部捨てて検出をやり直す。RiR の計算(`rir`)は捨てないので、拍が空いた分は UnevenFilter の「0.8秒以上空いた」分岐で扱われる。

**quality(信号品質)**
直近4秒(1000点)にハン窓を掛け、50Hzの成分の大きさを1つだけ計算する(FFT全体ではなく、200番目の周波数の成分だけ)。20未満で良好、200未満で注意、それ以上で不良。

**EcgSession(パケットの入口)**
パケット先頭の本体時刻を前のパケットと比べ、0.2秒より空いていれば、抜けたパケット数 × 50点を `gap` に伝える。日付をまたいだとき(時刻が大きく戻ったとき)は1日を足す。

### 4-6. Activity.swift(安静 / 軽い動き / 運動)

`realtime/activity.py` の書き写し。Python版で「静止」と呼ぶ状態を、アプリでは「安静」と表示している。

- 動きの大きさ M: 直近2秒のジャイロ3軸それぞれの標準偏差を、2乗して足して平方根を取る。さらに直近6秒の M の中央値を使う(一瞬の揺れで状態が変わらないように)。
- 心拍: 直近30秒の拍の中央値。拍が10未満、40〜200bpmの外、RRIのばらつきが大きいときは信用しない。
- 判定: M ≥ 1000 で運動。250 ≤ M < 1000 は、心拍が100bpm以上なら運動、それ以外は軽い動き。M < 250 は安静。
- 新しい状態が3秒続いてから切り替える(表示のちらつき防止)。

閾値は `ActivityConst` にまとめてある。仮の値なので、変えるときは Python版と一緒に直す。

### 4-7. Recording.swift(記録と流し直し)

1件 = `[種類 1バイト][長さ 1バイト][パケット]`。
`decode` は先頭から順に読み、末尾が途中で切れている件(書いている最中にアプリを終了された件)は捨てる。
`replay` は、記録を受信したときと同じ順に `EcgSession` へ流す。同じ順に流せば、解析の結果は受信したときと同じになる(テストで確かめている)。

## 5. テストの読み方(Analysis/Tests/EcgCoreTests/)

テストは「Python版の結果を正解として、Swift版が同じ結果を出すか」を確かめている。正解データは `Analysis/tools_make_fixtures.py` で、Python版を動かして作る。心電図とジャイロは計算で作った作り物で、実測データは入れていない(公開リポジトリのため)。

| テスト | 確かめていること |
|---|---|
| `testBandPassAndPeaks` | フィルタの出力の誤差が 1e-6 未満、ピークの位置が完全に一致 |
| `testRiRChain` | RRIの列を与えたときの RiR・ΣRiR・La がすべての拍で一致 |
| `testWholePipeline` | 心電図から通しで流したとき、拍の位置・RRI・RiR がすべて一致。信号品質も一致 |
| `testActivity` | パケットごとの状態・M・心拍が一致 |
| `testRecordingReplay` | 記録して流し直した結果が、直接受信した結果と同じ |

Windowsでは `cd Analysis` してから `swift test` で全部動く。1つだけなら `swift test --filter testRiRChain`。

## 6. 練習課題

1. `SignalTools.swift` の `median` に空の配列を渡すと何が起きるか。どこから呼ばれていて、空になることはあるか。
2. `MovAveFilter` の `buflen = intSpan × maxHR / 20` は、なぜこの長さで足りるのか(180秒の間に来る拍の最大数と比べる)。
3. `RealtimeECG.afterNewPeak` で、最後の1拍を保留しなかったら何が起きるか。
4. `ActivityConst.tLight` を 250 から 300 にしたら、`testActivity` はどうなるか。Python版も変えたときはどうか。
5. `findPeaks` の2段目を「高い順」ではなく「左から順」に処理したら、結果が変わる例を作れるか。
